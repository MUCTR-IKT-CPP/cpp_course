### Алгоритм вместо ручного цикла

Практический пример — поиск первого просроченного заказа. Ручной цикл должен хранить условие остановки, сравнивать итератор с концом и возвращать результат. `std::find_if` уже описывает этот маршрут, а переданный предикат оставляет в коде предметный вопрос: «просрочен ли заказ?».

Во время вызова алгоритм последовательно получает элементы диапазона и передаёт каждый вызываемому объекту. Как только предикат возвращает `true`, поиск завершается и возвращает итератор позиции. Если подходящего элемента нет, результат равен `end()`.

Ручной цикл иногда короче алгоритма, особенно если не считать три минуты, потраченные на поиск ошибки в границе.

Стандартная библиотека состоит не только из контейнеров. Заголовок `<algorithm>` предоставляет функции поиска, преобразования, сортировки, копирования и проверки условий.

Большинство классических алгоритмов принимает полуинтервал итераторов `[first, last)`:

```cpp
std::vector<int> values{1, 2, 3, 4};

std::for_each(values.begin(), values.end(), [](int value) {
    std::cout << value << '\n';
});
```

Итераторы отделяют алгоритм от конкретного контейнера. Один алгоритм может работать с `vector`, `list` или встроенным массивом, если категория итератора удовлетворяет требованиям.

### Примеры алгоритмов

```cpp
auto position{std::find(values.begin(), values.end(), 3)};
if (position != values.end()) {
    std::cout << "Найдено\n";
}

int even_count{std::count_if(values.begin(), values.end(), [](int value) {
    return value % 2 == 0;
})};

std::transform(values.begin(), values.end(), values.begin(), [](int value) {
    return value * value;
});
```

Сигнатуры различаются: одни алгоритмы только читают, другие меняют диапазон, третьи записывают результат через выходной итератор. Перед вызовом следует проверить контракт, а не угадывать его по имени.

### Предикат

Предикат получает значение и отвечает на один логический вопрос. Для фильтрации товаров это может быть проверка доступности, для сортировки — отношение порядка между двумя товарами. Алгоритм полагается не на название функции, а на её результат и требуемые свойства.

Если предикат хранит состояние, одинаковый элемент может оцениваться с учётом настроенного порога. При этом побочные эффекты следует использовать осторожно: алгоритм определяет допустимый порядок вызовов, а не обязательно тот порядок, который мы вообразили по одному запуску.


**Предикат** — вызываемый объект, результат которого используется как логическое условие:

```cpp
bool isEven(int value) {
    return value % 2 == 0;
}

auto count{std::count_if(values.begin(), values.end(), isEven)};
```

Алгоритм может копировать предикат и вызывать его в неизвестном нам порядке. Нельзя строить корректность на неожиданных побочных эффектах, если контракт алгоритма этого не обещает.

### Функциональный объект

Объект-функция объединяет поведение и данные. Экземпляр может хранить порог скидки, а `operator()` — проверять каждый заказ относительно этого порога. Алгоритм получает объект по значению или ссылке согласно своей сигнатуре и вызывает его как обычную функцию.

При копировании функционального объекта копируется и его состояние. Поэтому счётчик вызовов внутри конкретного экземпляра не всегда следует наблюдать через исходную переменную: алгоритм может работать с собственной копией в рамках разрешённого контракта.

Класс с `operator()` называется функциональным объектом, или функтором:

```cpp
class GreaterThan {
public:
    explicit GreaterThan(int threshold) : threshold_{threshold} {}

    bool operator()(int value) const {
        return value > threshold_;
    }

private:
    int threshold_;
};

auto count{std::count_if(values.begin(), values.end(), GreaterThan{10})};
```

Функтор хранит состояние и остаётся обычным типом. Лямбда предоставляет компактный синтаксис для создания похожего безымянного объекта.

### Лямбда-выражение

Лямбда создаёт объект без необходимости отдельно называть его класс. Список параметров описывает данные конкретного вызова, тело — действие, а список захвата определяет внешнее состояние, которое станет частью замыкания.

В месте создания компилятор формирует уникальный тип замыкания. Передача лямбды в алгоритм означает передачу объекта этого типа; последующий вызов выполняет сгенерированный `operator()`.

Лямбда называется безымянной функцией, но компилятор всё равно даёт её типу имя — просто никому его не показывает.

```cpp
[capture](parameters) specifiers -> return_type {
    body
}
```

Минимальная лямбда:

```cpp
[] {
    std::cout << "Hello\n";
}();
```

Выражение создаёт объект уникального безымянного типа замыкания. Скобки `()` после тела сразу вызывают созданный объект.

### Параметры и возвращаемый тип

```cpp
auto sum{[](int left, int right) {
    return left + right;
}};

std::cout << sum(2, 3) << '\n';
```

Возвращаемый тип обычно выводится. Его указывают явно, если ветви возвращают значения, для которых вывод неоднозначен:

```cpp
auto normalize{[](double value) -> double {
    if (value < 0.0) {
        return 0.0;
    }
    return value;
}};
```

### Захват внешних имён

Захват по значению сохраняет копию выбранного внешнего значения внутри объекта замыкания. Изменение исходной переменной после создания не меняет эту копию. Захват по ссылке хранит связь с исходным объектом, поэтому видит дальнейшие изменения, но требует, чтобы объект продолжал существовать.

Практический сценарий — фильтр заказов по выбранному пользователем порогу. Захват значения фиксирует настройку на момент создания фильтра. Захват ссылки позволяет читать актуальную настройку, но становится опасным, если фильтр переживёт окно или объект конфигурации.

Захват `[&]` очень гостеприимен: приглашает всё окружение, а разбираться со временем жизни предлагает хозяину программы.

Пустой список `[]` запрещает использовать автоматические локальные переменные извне. Захват по значению копирует значение в объект замыкания:

```cpp
int threshold{10};
auto greater{[threshold](int value) {
    return value > threshold;
}};
```

Захват по ссылке связывает замыкание с существующим объектом:

```cpp
int count{0};
std::for_each(values.begin(), values.end(), [&count](int value) {
    if (value > 0) {
        ++count;
    }
});
```

Ссылка не продлевает время жизни. Лямбда, сохранённая дольше захваченной локальной переменной, получит висячую ссылку.

Захваты по умолчанию `[=]` и `[&]` удобны в коротком локальном вызове, но явный список лучше документирует зависимости.

### Инициализирующий захват и `mutable`

```cpp
auto pointer{std::make_unique<int>(42)};
auto reader{[owned = std::move(pointer)] {
    return *owned;
}};
```

Инициализирующий захват позволяет переместить ресурс в замыкание.

По умолчанию `operator()` у лямбды является `const`, поэтому копии, захваченные по значению, менять нельзя. `mutable` разрешает менять состояние копии:

```cpp
auto counter{[value = 0]() mutable {
    return ++value;
}};
```

Внешняя переменная при этом не меняется.

### Обобщённая лямбда

```cpp
auto maximum{[](const auto& first, const auto& second) {
    return first > second ? first : second;
}};
```

Параметры `auto` превращают оператор вызова в шаблон. Начиная с C++20 доступен явный список шаблонных параметров:

```cpp
auto sizeInBytes{[]<typename T>(const T& value) {
    return sizeof(value);
}};
```

### Алгоритмы и пользовательские типы

Для сортировки пользовательского типа передают компаратор:

```cpp
struct Record {
    int key;
    int original_index;
};

std::sort(records.begin(), records.end(), [](const Record& left,
                                              const Record& right) {
    return left.key < right.key;
});
```

Компаратор должен задавать строгое слабое упорядочение. В частности, `compare(x, x)` должен быть ложным; использование `<=` вместо `<` обычно нарушает контракт.

### `sort` и `stable_sort`

Сортировка многократно вызывает компаратор для пар элементов и переставляет элементы диапазона. Компаратор должен задавать строгий слабый порядок; в частности, элемент не должен быть меньше самого себя. Нарушение требований ломает предположения алгоритма.

`stable_sort` дополнительно сохраняет относительный порядок эквивалентных элементов. Это полезно при последовательной сортировке записей: сначала по вторичному признаку, затем стабильно по основному. Обычный `sort` такой гарантии не даёт.

Стабильная сортировка сохраняет порядок равных элементов — редкая ситуация, когда алгоритм официально уважает очередь.

`std::sort` не сохраняет относительный порядок эквивалентных элементов. `std::stable_sort` сохраняет:

```cpp
std::stable_sort(records.begin(), records.end(), [](const auto& left,
                                                     const auto& right) {
    return left.key < right.key;
});
```

Стабильность нужна, когда предыдущий порядок содержит смысл. За неё приходится платить возможными дополнительными ресурсами и иными характеристиками реализации.

`std::sort` требует итераторов произвольного доступа, поэтому не применяется к `std::list`; у списка есть собственный метод `sort`.

### Случайные числа

Генератор хранит внутреннее состояние и по каждому вызову выдаёт следующее псевдослучайное значение. Распределение преобразует этот поток в требуемый диапазон и форму. Поэтому двигатель и распределение решают разные задачи и передаются в пример отдельно.

Фиксированное зерно полезно в тесте: одна и та же последовательность делает ошибку воспроизводимой. Случайное зерно подходит для разнообразия демонстрации, но не превращает обычный генератор в криптографический источник.

Случайные числа в тесте особенно случайны в тот день, когда ошибка воспроизводится только у преподавателя.

Современная библиотека разделяет двигатель и распределение:

```cpp
#include <random>

std::random_device seed;
std::mt19937 engine{seed()};
std::uniform_int_distribution<int> distribution{-100, 100};

int value{distribution(engine)};
```

Двигатель создают один раз и используют многократно. Создание нового `random_device` и двигателя для каждого элемента дорого и затрудняет воспроизводимость.

Для тестов удобно передать фиксированное зерно:

```cpp
std::mt19937 engine{42};
```

Так последовательность повторяется. Для непредсказуемых криптографических значений `mt19937` не подходит.

### Унификация поведения

В приведённом `generate` цикл отвечает за количество вызовов генератора, а `push_back` — за добавление результата в контейнер. После каждой итерации размер контейнера увеличивается на один, и возвращаемый объект владеет накопленными элементами.

Это намеренно ограниченный пример для контейнеров с интерфейсом `push_back`. Он показывает передачу поведения и не обязан без изменений принимать любой контейнер стандартной библиотеки. Для `set` способ вставки адаптируют к его интерфейсу и требованиям уникальности; общий замысел при этом сохраняется.

Генерацию контейнера можно параметризовать распределением или функцией:

```cpp
template <typename Container, typename Generator>
Container generate(std::size_t count, Generator generator) {
    Container result;
    for (std::size_t index{0}; index < count; ++index) {
        result.push_back(generator());
    }
    return result;
}
```

Теперь алгоритм отвечает за количество и вставку, а переданный объект — за получение значения. Это тот же принцип передачи поведения, который мы видели в шаблонах.

### Замечания к примерам лекции

В `base.h` используется нестандартный макрос `__PRETTY_FUNCTION__`. Это намеренная демонстрация того, как GCC и Clang могут показать сформированную сигнатуру функции или специализации. Такой вывод полезен для наблюдения за выводом типов, но пример не заявляет переносимость и не предназначен как промышленный интерфейс журналирования.

Отдельные захваты и формы параметров в демонстрациях выбраны ради наглядности конкретного механизма. Их можно сузить при развитии кода, однако это не меняет учебный результат примера.

Шаблон `generate` предполагает наличие `push_back`, потому что демонстрирует конкретный способ наполнения последовательного контейнера. При запуске с `set` функция адаптируется: вместо `push_back` используется поддерживаемая операция вставки, а также учитывается уникальность ключей. Требовать от короткого примера универсальности всех контейнеров означало бы заслонить изучаемую возможность инфраструктурой.

### Итоги

#### Сквозной разбор обработки диапазона

Пусть требуется выбрать активные заказы и отсортировать их по стоимости. Диапазон задаётся парой итераторов, предикат описывает активность, а компаратор — отношение порядка между двумя заказами.

Алгоритм не владеет контейнером и не продлевает жизнь его элементов. Итераторы должны оставаться действительными на протяжении вызова, а переданные функциональные объекты — корректно работать с каждым допустимым элементом.

Лямбда с порогом по значению фиксирует настройку в момент создания. Захват по ссылке читает текущее значение, но требует, чтобы переменная пережила использование замыкания. Если лямбда сохраняется для будущего вызова, это различие становится частью контракта времени жизни.

Во время сортировки компаратор вызывается многократно и не должен изменять сравниваемые ключи так, чтобы отношение порядка менялось в процессе. Для эквивалентных элементов `stable_sort` сохраняет исходную относительную последовательность.

Генерация данных добавляет ещё два объекта: двигатель с внутренним состоянием и распределение, преобразующее его значения. Фиксированное зерно делает последовательность воспроизводимой, что полезно для диагностики тестового сценария.

Перед применением алгоритма полезно проверить:

- соответствует ли категория итератора требованиям операции;
- не изменяет ли предикат состояние, от которого зависит собственный ответ;
- достаточно ли долго живут захваченные по ссылке объекты;
- задаёт ли компаратор строгий слабый порядок;
- отвечает ли способ вставки интерфейсу выбранного контейнера;
- является ли платформозависимая диагностика частью демонстрации, а не обещанием переносимости.

Эти вопросы объясняют механику примеров без требования превратить каждый учебный фрагмент в универсальную промышленную библиотеку.

#### Наблюдение за результатом

До вызова алгоритма полезно зафиксировать исходный диапазон, а после — положение возвращённого итератора или новый порядок элементов. Так текст связывает абстрактное имя алгоритма с конкретным изменением данных.

Для немодифицирующих алгоритмов исходный контейнер остаётся прежним, а результат выражается итератором, числом или логическим значением. Для сортировки меняется порядок самих элементов в переданном диапазоне.

Диагностическая `print` с `__PRETTY_FUNCTION__` помогает увидеть конкретную специализацию на выбранном компиляторе. Она наблюдает процесс вывода типов и не входит в предметный алгоритм.

При адаптации `generate` к другому контейнеру изменяется операция вставки, но число обращений к генератору и разделение обязанностей остаются прежними.

Так ограниченный пример остаётся полезным и не притворяется универсальным интерфейсом.

Адаптация начинается только после появления конкретного нового требования.

Алгоритм выражает намерение над диапазоном, а предикат или лямбда передаёт изменяемую часть поведения. Захваты делают лямбду состоянием, поэтому требуют контроля времени жизни. Корректный компаратор и подходящая категория итератора важнее краткости записи.
