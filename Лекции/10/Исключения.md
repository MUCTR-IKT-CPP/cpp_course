### Что мы называем исключением

#### От необычной ситуации к механизму языка

Представим функцию, которая читает конфигурацию приложения. Отсутствие необязательного параметра может быть штатным состоянием, а невозможность прочитать обязательный файл делает продолжение операции бессмысленным. Оба события необычны относительно основного пути, но только второе может потребовать передачи управления обработчику ошибки.

**Исключение** в C++ — объект, передаваемый механизмом `throw`/`catch`. Он отделяет место обнаружения проблемы от места, где достаточно контекста для решения. При этом само наличие исключения не определяет политику: обработчик может восстановиться, преобразовать ошибку, записать диагностику или завершить текущую операцию.

Полезно разделять три уровня: факт нарушения ожидаемого хода, способ сообщить о нём и решение вызывающего кода. Исключения отвечают прежде всего за второй уровень.

Исключение — не паранормальное явление: обычно у него есть вполне земная причина и номер строки в журнале.

Программа сталкивается с разными проблемами: неверным пользовательским вводом, отсутствующим файлом, нехваткой памяти, нарушенным внутренним инвариантом. Не все они одинаковы и не каждую следует выражать исключением.

**Исключительная ситуация** — обстоятельство, при котором операция не может выполнить заявленный контракт обычным способом. **Исключение C++** — объект, передаваемый механизмом `throw`/`try`/`catch` для сообщения о такой ситуации.

Ожидаемый результат, например «ключ не найден» при обычном поиске, часто удобнее вернуть как `std::optional`, специальный статус или другой явный тип результата. Исключения подходят для отделения основного пути от ошибки, которую текущий уровень не может обработать локально.

### Стратегии обработки ошибок

#### Выбор формы результата

Код возврата удобен, когда вызывающий код ожидает несколько обычных исходов и должен разобрать их сразу. Необязательное значение подходит, когда достаточно различать «есть результат» и «результата нет». Исключение полезно, когда функция не может выполнить обещанную операцию, а решение находится выше по стеку вызовов.

Рассмотрим поиск пользователя. Отсутствие записи может быть нормальным результатом запроса и выражаться через `std::optional`. Потеря соединения с хранилищем — уже другая категория: запрос не был выполнен, и вызывающему уровню может понадобиться повтор, резервный источник или сообщение пользователю.

Механизм выбирают по контракту, а не по привычке. Если каждое деление нацело выбрасывает исключение при остатке, вызывающий код получит драматургию там, где достаточно обычной ветви.

Коды ошибок очень вежливы: они никогда не прерывают программу сами, даже когда их никто не проверяет.

Существуют разные способы:

- вернуть код состояния;
- вернуть объект результата, содержащий значение или ошибку;
- установить состояние объекта, как делают потоки;
- завершить программу при невосстановимом нарушении;
- выбросить исключение.

Выбор является частью контракта функции. Нельзя смешивать способы случайно: вызывающий код должен понимать, где искать ошибку и кто отвечает за восстановление.

### `try`, `throw` и `catch`

#### Путь управления

Блок `try` отмечает область, из которой исключение может быть перехвачено расположенными после неё обработчиками. Выражение `throw` сначала создаёт или инициализирует объект исключения, после чего обычное выполнение текущего блока прекращается.

Программа не возвращается к следующей строке после `throw`. Она ищет подходящий обработчик, покидая промежуточные области видимости. Если обработчик найден, его параметр связывается с объектом исключения, выполняется тело `catch`, а затем управление продолжается после всей конструкции обработчиков.

В примере деления важна не только проверка нуля. Функция обнаруживает невозможность выполнить свой контракт и передаёт описание проблемы. Вызвавшая функция решает, что показать пользователю и можно ли продолжить другую часть работы.

Исключение умеет быстро подниматься по стеку — карьерная траектория, о которой мечтают многие объекты.

```cpp
double divide(double numerator, double denominator) {
    if (denominator == 0.0) {
        throw std::invalid_argument{"division by zero"};
    }
    return numerator / denominator;
}

try {
    std::cout << divide(10.0, 0.0) << '\n';
} catch (const std::invalid_argument& error) {
    std::cerr << error.what() << '\n';
}
```

`throw` создаёт или передаёт объект исключения. Выполнение обычного пути немедленно прекращается. Система ищет ближайший подходящий обработчик среди активных вызовов.

Исключения классов обычно ловят по `const&`, чтобы избежать срезки и лишнего копирования:

```cpp
catch (const std::exception& error) {
    std::cerr << error.what() << '\n';
}
```

Параметр одного `catch` недоступен в соседнем обработчике; обработчики являются отдельными областями видимости.

### Раскрутка стека

#### Что уничтожается по дороге

Когда исключение покидает функцию, её локальные автоматические объекты завершают время жизни в порядке, обратном построению. Вызываются деструкторы полностью созданных объектов. Затем процесс повторяется для следующей функции, пока не будет найден обработчик.

Представим сохранение отчёта. Локальный объект владеет временным файлом, другой объект — блокировкой. Если запись завершается исключением, деструкторы освобождают оба ресурса до входа в обработчик. Именно поэтому RAII превращает множество аварийных путей в один механизм очистки.

Объект, конструктор которого не завершился, целиком не существует и его деструктор не вызывается. Однако уже построенные базовые части и поля будут уничтожены. Это позволяет безопасно составлять сложный объект из владельцев ресурсов.


При поиске обработчика C++ покидает активные блоки и вызывает деструкторы полностью созданных автоматических объектов. Это **раскрутка стека**.

```cpp
void process(const std::filesystem::path& path) {
    std::ifstream input{path};
    if (!input) {
        throw std::runtime_error{"cannot open file"};
    }
    // input закроется и при обычном выходе, и при исключении
}
```

C++ не имеет универсального блока `finally`. Его роль выполняют RAII-объекты. Ресурс, управляемый сырым `new`, ручной блокировкой или незакрытым дескриптором, легко потерять при исключении.

### Поиск обработчика

#### Соответствие типов и порядок

Поиск начинается в ближайшем окружающем `try`. Обработчики проверяются сверху вниз, поэтому более конкретные типы следует располагать раньше базовых. Обработчик `const std::exception&` способен принять множество стандартных исключений и должен находиться после специализированных вариантов.

Передача по ссылке сохраняет динамический тип объекта и избегает лишнего копирования. Перехват по значению базового типа способен привести к срезке, как и обычная передача объектов по значению.

Если подходящего обработчика в текущей функции нет, поиск продолжается у вызывающей стороны после уничтожения локальных объектов. Если обработчик не найден вообще, вызывается `std::terminate`.

`catch (...)` поймает почти всё, но не объяснит, что именно поймал; это как подписать коробку словом «предметы».

Обработчики проверяются сверху вниз. Производный тип нужно ловить раньше базового:

```cpp
try {
    performOperation();
} catch (const std::invalid_argument& error) {
    // конкретная ошибка
} catch (const std::exception& error) {
    // остальные стандартные исключения
} catch (...) {
    // неизвестный тип
}
```

`catch (...)` должен быть последним. Он не предоставляет объект ошибки, но позволяет выполнить граничную обработку. Пустой catch без восстановления обычно скрывает неисправность.

Если обработчик не найден, вызывается `std::terminate`. То же происходит, когда исключение выходит из функции, обещавшей `noexcept`.

### Повторное выбрасывание

Обработчик иногда располагает локальным контекстом для журналирования, но не знает, как восстановить операцию. Запись `throw;` повторно передаёт текущее исключение, сохраняя его исходный объект и динамический тип.

Запись `throw exception;` создаёт новое выбрасывание выражения. Если параметр имеет базовый тип, возможно копирование или срезка. Поэтому для продолжения того же исключения используется форма без операнда.

Практический сценарий: слой доступа к файлам добавляет в журнал имя пути и повторно выбрасывает ошибку, а уровень пользовательской операции решает, предложить ли другой файл. Каждый уровень делает только то, для чего у него есть контекст.

Внутри обработчика `throw;` повторно передаёт текущее исключение без копирования и с сохранением динамического типа:

```cpp
catch (const std::exception& error) {
    log(error.what());
    throw;
}
```

Запись `throw error;` создаёт новое исключение из статического типа переменной и способна выполнить срезку. Логировать одну ошибку на каждом уровне тоже не стоит: результатом становится несколько одинаковых сообщений без дополнительного контекста.

### Стандартная иерархия

Общий базовый тип `std::exception` предоставляет виртуальный `what()`. Производные классы различают категории проблем, чтобы обработчик мог выбрать политику. Например, ошибка аргумента и сбой выполнения могут требовать разных сообщений и разных действий.

Не обязательно строить глубокую иерархию для каждой функции. Тип исключения полезен, если вызывающий код действительно принимает по категории отдельное решение. Иначе достаточно содержательного сообщения и существующего подходящего класса.

Базовый тип большинства стандартных исключений — `std::exception`. Метод `what()` возвращает диагностическое сообщение.

Часто встречаются:

- `std::logic_error` и производные — ошибка в условиях или логике вызова;
- `std::invalid_argument` — недопустимый аргумент;
- `std::out_of_range` — выход за допустимый диапазон проверяемой операции;
- `std::runtime_error` — проблема, обнаруженная во время выполнения;
- `std::bad_alloc` — неудачное обычное выделение через `new`.

Разделение `logic_error`/`runtime_error` не заменяет проектирование собственного контракта, но помогает классифицировать распространённые ситуации.

### Пользовательское исключение

#### Данные для решения, а не для украшения

Пользовательский тип оправдан, когда ошибка относится к предметной области и несёт данные, нужные обработчику. Например, исключение проверки заказа может хранить идентификатор и категорию нарушения. Текст `what()` помогает человеку, а структурированные поля позволяют программе не разбирать строку.

В листинге конструктор базового `std::runtime_error` сохраняет сообщение. Когда объект выбрасывается, он копируется или перемещается в специальное хранилище исключения и существует достаточно долго для обработки. Перехват по `const&` связывается с этим объектом без дополнительной копии.

Не следует использовать исключение как ещё один способ вернуть обычное значение. Оно сообщает, что обещанная операция не завершилась обычным образом.

```cpp
class ConfigurationError : public std::runtime_error {
public:
    ConfigurationError(std::string key, std::string message)
        : std::runtime_error{std::move(message)}, key_{std::move(key)} {}

    const std::string& key() const noexcept {
        return key_;
    }

private:
    std::string key_;
};
```

Исключение должно нести данные, необходимые обработчику. Текст `what()` полезен для человека, но программную логику лучше строить на типе и структурированных полях, а не на разборе строки.

### Гарантии безопасности исключений

#### Как оценить состояние после неудачи

Гарантия отсутствия исключений означает, что операция обещает не выбрасывать; это особенно важно для деструкторов и некоторых перемещающих операций. Сильная гарантия оставляет наблюдаемое состояние таким, каким оно было до вызова. Базовая гарантия допускает изменение, но сохраняет корректность объектов и отсутствие утечек.

Рассмотрим добавление элемента в структуру. Для сильной гарантии можно сначала подготовить новое состояние во временном объекте, а затем выполнить короткую безопасную замену. Если подготовка завершится ошибкой, исходная структура останется прежней.

Не каждая операция обязана давать сильную гарантию. Важно явно понимать обещанный уровень и не оставлять объект в состоянии, нарушающем его инварианты.


Операцию оценивают по тому, в каком состоянии она оставляет программу при исключении:

- **отсутствие гарантии** — состояние может быть нарушено;
- **базовая гарантия** — инварианты сохранены, ресурсы не потеряны, но состояние могло измениться;
- **строгая гарантия** — операция либо завершилась, либо наблюдаемое состояние осталось прежним;
- **гарантия отсутствия исключений** — операция не выбрасывает, что выражают `noexcept` там, где обещание действительно выполняется.

Идемпотентность — другое свойство: повтор операции даёт тот же эффект, что и один вызов. Она помогает безопасно повторять некоторые операции после сбоя, но не является синонимом безопасности исключений.

### Локальность обработки

Обрабатывать исключение следует там, где есть информация для осмысленного решения. Низкоуровневая функция знает, что чтение не удалось, но может не знать, важен ли файл для пользователя. Верхний уровень знает сценарий, но не должен угадывать системную причину.

Поэтому нижний уровень формирует точное описание, промежуточный при необходимости добавляет контекст, а граница операции выбирает восстановление или сообщение. Перехват с немедленным молчаливым продолжением опасен: программа скрывает невыполненное действие и может использовать неполное состояние.

Ловить исключение нужно на уровне, где достаточно контекста для решения:

- повторить операцию, если повтор безопасен;
- откатить транзакцию;
- преобразовать низкоуровневую ошибку в ошибку предметной области;
- сообщить пользователю и выбрать дальнейший сценарий;
- завершить границу потока или процесса контролируемо.

Если модуль не знает, как восстановиться, он не должен ловить ошибку только ради продолжения. RAII освободит локальные ресурсы без catch.

### Исключения в конструкторах и деструкторах

Конструктор выбрасывает исключение, если не может создать корректный объект. Пользователь не получает «наполовину готовый» экземпляр; уже построенные части очищаются автоматически. Это естественный способ обеспечить инвариант с самого начала времени жизни.

Деструктор, выполняющийся во время раскрутки стека, не должен выпускать новое исключение. Два одновременно активных исключения приводят к завершению программы. Поэтому освобождение ресурса проектируют как надёжную операцию, а ошибки явного завершения при необходимости обрабатывают до деструктора.

Конструктор может выбросить исключение: уже созданные базовые части и поля будут уничтожены, а сам объект не считается созданным.

Деструктор по умолчанию `noexcept`. Исключение, вышедшее из деструктора во время раскрутки стека, приводит к `std::terminate`. Поэтому деструкторы должны завершать освобождение ресурсов без передачи ошибки наружу.

### Производительность

Обычный путь без выбрасывания во многих реализациях имеет небольшую дополнительную стоимость, но создание исключения, поиск обработчика и раскрутка стека значительно дороже простого условного перехода. Точные числа зависят от реализации и структуры программы.

Главный вывод не в том, что исключения «медленные», а в соответствии частоте события. Если отсутствие элемента ожидается каждую вторую итерацию, это обычная ветвь. Если операция редко не может выполнить контракт, стоимость исключительного пути может быть приемлемой.

Во многих реализациях путь без исключения имеет небольшие накладные расходы, а сам `throw` и раскрутка стека дороги. Это не универсальная числовая гарантия.

Исключения не стоит использовать как обычное управление циклом или ожидаемое ветвление. Но заменять их кодами возврата только из страха перед производительностью тоже не следует без измерений и требований проекта.

### `assert`

`assert` проверяет предположение разработчика в отладочной конфигурации. Он подходит для внутренних инвариантов, нарушение которых означает дефект программы, а не некорректный пользовательский ввод.

При определённом `NDEBUG` выражение проверки удаляется. Поэтому внутри него нельзя размещать необходимое действие с побочным эффектом. Проверка внешнего файла или сетевого ответа тоже не должна зависеть от `assert`: такая ошибка возможна в корректной программе и требует обычной обработки.

`assert` — строгий преподаватель: в отладке задаёт вопросы, а перед выпуском неожиданно уходит в отпуск.

```cpp
#include <cassert>

int elementAt(const std::array<int, 10>& values, std::size_t index) {
    assert(index < values.size());
    return values[index];
}
```

`assert` проверяет предположение разработчика и завершает программу при ложном условии в активной отладочной конфигурации. При определённом `NDEBUG` выражение не вычисляется.

Поэтому `assert` нельзя использовать для проверки пользовательского ввода, ошибок сети или другой ситуации, которую программа обязана обработать в release-сборке. В условии assert также не должно быть необходимых побочных эффектов.

В примере слайда проверка `index <= 8` для массива из 10 элементов ошибочно запрещает индекс 9. Корректная проверка — `index < array.size()`.

### Итоги

#### Сквозной сценарий: загрузка заказа

Представим операцию, которая читает файл заказа, разбирает поля и создаёт предметный объект. На каждом уровне возможна своя проблема: файл недоступен, формат нарушен, обязательное поле отсутствует или значение не удовлетворяет правилам заказа.

Функция чтения обнаруживает инфраструктурную причину и сообщает её подходящим типом исключения. Разбор добавляет контекст о поле или позиции. Уровень пользовательской операции знает имя выбранного заказа и решает, можно ли предложить повторный ввод.

После `throw` обычный путь текущей функции прекращается. Локальный файловый поток уничтожается при раскрутке стека и закрывает ресурс. Полностью созданные временные строки и контейнеры также завершают время жизни в обратном порядке.

Если обработчик для конкретной ошибки формата расположен раньше `std::exception`, он может показать точную диагностику. Базовый обработчик остаётся запасным вариантом для других стандартных исключений. `catch (...)` применяется только тогда, когда политика действительно не зависит от типа.

#### Состояние операции после ошибки

До начала изменения полезно определить требуемую гарантию. Если заказ заменяется новым, сильную гарантию можно получить подготовкой нового объекта во временном состоянии. Только после успешного чтения и проверки временный объект перемещается на место старого.

Если ошибка возникнет во время подготовки, прежний заказ останется наблюдаемо неизменным. Временные ресурсы очистятся через RAII. Эта последовательность связывает гарантию исключений с обычными конструкторами и деструкторами.

Для большой пошаговой операции сильная гарантия может быть слишком дорогой. Тогда базовая гарантия допускает частичное изменение, но объект обязан оставаться корректным и пригодным для дальнейших разрешённых действий.

#### Где принимать решение

Нижний уровень не должен спрашивать пользователя о повторе: у библиотечной функции нет такого контекста. Верхний уровень не должен угадывать, какая системная операция завершилась неудачно. Каждый слой добавляет сведения, которыми действительно располагает.

Полезная схема выглядит следующим образом:

1. Обнаружить невозможность выполнить локальный контракт.
2. Создать содержательное описание ошибки.
3. Позволить автоматическим объектам освободить ресурсы.
4. На подходящем уровне выбрать восстановление или завершение операции.
5. Не скрывать ошибку, если обещанный результат не был получен.

#### Проверка конструктора и деструктора

Если конструктор заказа не может установить инвариант, он выбрасывает исключение, и пользователь не получает частично созданный объект. Уже созданные поля очищаются автоматически.

Деструкторы владельцев не выпускают исключения наружу во время раскрутки. Если завершение ресурса способно дать значимую ошибку, явная операция закрытия выполняется раньше, когда вызывающий код ещё может принять решение.

#### Исключение или обычная ветвь

Отсутствие необязательной скидки — ожидаемый результат и может быть представлено обычным значением. Повреждённый обязательный файл означает, что загрузка не выполнила контракт. Различие определяется смыслом операции, а не удобством синтаксиса.

При выборе механизма следует оценить частоту события, необходимый контекст и способ продолжения. Исключения особенно полезны, когда промежуточные функции не способны решить проблему, но обязаны корректно освободить свои ресурсы.

Так сквозной сценарий связывает `throw`, поиск обработчика, раскрутку стека, RAII и гарантии в одну модель управления неудавшейся операцией.

#### Диагностика без потери причины

Сообщение должно добавлять контекст, а не заменять исходную причину общей фразой. Имя файла, операция и предметный идентификатор помогают понять сценарий, тогда как тип исключения позволяет программе выбрать политику.

Если уровень не способен восстановиться, после добавления контекста он передаёт проблему дальше. Молчаливый `catch` создаёт видимость успеха, хотя обещанный результат отсутствует.

При тестировании такого пути проверяют не только тип исключения, но и состояние объектов после выхода. Ресурсы должны быть освобождены, а данные — соответствовать заявленной гарантии.

Эта проверка завершает причинную цепочку от места обнаружения до наблюдаемого состояния вызывающей стороны.

По ней можно восстановить не только место сбоя, но и выполненную очистку.

Это делает обработку ошибки проверяемой частью контракта операции.

Исключение передаёт проблему на уровень, способный принять решение, а RAII сохраняет ресурсы во время раскрутки. Классы исключений должны выражать смысл, `catch` — выполнять реальное восстановление или преобразование, а `assert` — проверять внутренние предположения, не заменяя обработку внешних ошибок.
