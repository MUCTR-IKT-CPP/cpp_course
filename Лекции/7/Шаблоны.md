### Когда перегрузок становится слишком много

Практический пример — функция выбора максимального значения для целых чисел, вещественных чисел и пользовательских величин. Если алгоритм одинаков, отдельные перегрузки повторяют не предметный смысл, а различия типов. Шаблон позволяет описать форму вычисления один раз и отложить выбор конкретного типа до места использования.

При вызове компилятор выводит аргументы шаблона, подставляет их в определение и формирует специализацию. Затем эта специализация проверяется как обычный код: наличие операторов и допустимость выражений определяются уже для конкретного типа.

Десять одинаковых перегрузок выглядят как семейная фотография: все очень похожи, но удалить кого-то страшно.

Предположим, нам нужна функция выбора большего значения. Для `int`, `double` и `char` можно написать три перегрузки, но их тела будут одинаковыми. Мы меняем тип, хотя алгоритм остаётся прежним.

**Шаблон** описывает семейство функций или классов, параметризованное типами и значениями. Конкретный вариант создаётся при подстановке аргументов шаблона — этот процесс называется инстанцированием.

```cpp
template <typename T>
const T& maximum(const T& first, const T& second) {
    return first > second ? first : second;
}
```

`typename` и `class` в объявлении типового параметра в большинстве случаев равнозначны. Имя `T` — не тип само по себе, а место для типа, который появится при инстанцировании.

```cpp
int integer{maximum(13, 10)};
double real{maximum(0.97, 1.76)};
```

Компилятор выводит `T` из аргументов. Если типы различаются и единого вывода нет, аргумент можно указать явно или спроектировать шаблон с несколькими параметрами:

```cpp
template <typename Left, typename Right>
auto add(const Left& left, const Right& right) {
    return left + right;
}
```

Шаблон работает не с «любыми типами», а с типами, для которых допустимы использованные операции. `maximum` требует сравнения `>` и совместимого результата условного выражения.

### Сокращённый шаблон функции

Параметр с `auto` в C++20 делает функцию шаблонной. Для каждого такого параметра выводится тип, а тело должно быть корректно для полученной комбинации. Короткая запись удобна, когда требования очевидны из небольшого выражения.

Если же функция предполагает сравнение, сложение и ещё несколько операций, явное ограничение через концепт делает контракт понятнее. Иначе пользователь узнает требования только из ошибки глубоко внутри тела.

`auto` сокращает объявление, но не сокращает время, которое иногда требуется на чтение сообщения компилятора.

Начиная с C++20 параметр `auto` в обычной функции создаёт сокращённый шаблон:

```cpp
const auto& maximum(const auto& first, const auto& second) {
    return first > second ? first : second;
}
```

Здесь два `auto` являются независимыми параметрами типов. Это не полностью эквивалентно варианту с одним `T`, который требует одинакового выведенного типа обоих аргументов.

### Возврат ссылки и время жизни

В исходных примерах `maximum` возвращает `const T&`. Это эффективно для существующих объектов, но опасно при временных аргументах:

```cpp
const int& dangling{maximum(10, 20)}; // ссылка переживает временные аргументы
```

Для маленьких значений безопаснее вернуть результат по значению:

```cpp
template <typename T>
T maximum(T first, T second) {
    return first > second ? first : second;
}
```

Универсальный библиотечный интерфейс требует аккуратной работы с категориями значений; простая ссылка не является автоматической оптимизацией.

### Шаблонный класс

Шаблон класса описывает семейство типов. `Array<int, 10>` и `Array<double, 10>` имеют общее исходное описание, но являются разными типами со своими специализациями. Их объекты нельзя смешивать только потому, что структура кода похожа.

В примере массива параметр типа определяет элементы, а нетиповой параметр — размер. При создании объекта компилятор получает оба значения и может проверить выражения, размер хранения и доступность операций для элемента.

Практически шаблонный класс полезен, когда правила владения и интерфейс одинаковы для разных типов данных: например, буфер чисел и буфер измерений работают одинаково, хотя смешивать сами элементы нельзя.

```cpp
template <typename T>
class Box {
public:
    explicit Box(T value) : value_{std::move(value)} {}

    T& value() { return value_; }
    const T& value() const { return value_; }

private:
    T value_;
};

Box<int> integer_box{42};
Box<std::string> text_box{"C++"};
```

`Box<int>` и `Box<std::string>` — разные типы. Начиная с C++17 в подходящих случаях работает вывод аргументов шаблона класса: `Box box{42};`.

### Определение метода вне шаблонного класса

```cpp
template <typename T>
class Array {
public:
    T& operator[](std::size_t index);
};

template <typename T>
T& Array<T>::operator[](std::size_t index) {
    return data_[index];
}
```

Нужно повторить `template <typename T>` и указать `Array<T>`, потому что определение относится ко всему семейству классов.

Если имя зависит от параметра шаблона и компилятор не знает, является ли оно типом, применяется `typename`:

```cpp
template <typename Container>
void printFirst(const Container& container) {
    typename Container::const_iterator iterator{container.begin()};
    std::cout << *iterator << '\n';
}
```

### Где хранить определения

Компилятор должен видеть определение шаблона в точке, где создаётся специализация. Одного объявления часто недостаточно: невозможно сгенерировать тело функции для `double`, не зная самого тела. Поэтому определения обычно помещают в заголовок или включаемый файл реализации.

Явное инстанцирование меняет организацию: одна единица трансляции создаёт заранее выбранные специализации, а остальные используют их объявления. Это уменьшает повторную работу, но ограничивает набор типов, доступных без дополнительной сборки.

Шаблон, спрятанный от компилятора в `.cpp`, напоминает рецепт в закрытом сейфе: название блюда известно, приготовить его всё равно нельзя.

Компилятору обычно нужно видеть определение шаблона в месте инстанцирования. Поэтому определения размещают в заголовке или подключаемом `.tpp`/`.ipp` файле.

Разнести шаблон между `.h` и `.cpp` можно при явном инстанцировании ограниченного набора вариантов:

```cpp
// array.cpp
template class Array<int>;
template class Array<double>;
```

Тогда другие типы недоступны без нового явного инстанцирования. Это осознанный компромисс, а не обычная схема для универсального контейнера.

### Нетиповые параметры

Параметром шаблона может быть значение, известное при компиляции:

```cpp
template <typename T, std::size_t Size>
class StaticArray {
private:
    T data_[Size]{};
};

StaticArray<int, 10> values;
```

Размер становится частью типа: `StaticArray<int, 10>` и `StaticArray<int, 20>` различны.

### Цена шаблонов

Шаблоны дают обобщение без обязательного виртуального вызова, но имеют недостатки:

- сообщения об ошибках могут быть длинными;
- реализация раскрывается в заголовках;
- множество инстанцирований увеличивает время сборки и размер кода;
- неявные требования к типу сложно понять без ограничений;
- небольшое изменение заголовка заставляет перекомпилировать зависимые единицы.

Эти проблемы не делают шаблоны плохими. Они напоминают, что обобщение должно иметь понятный контракт.

### Концепты C++20

#### Проверяемый контракт

Концепт даёт имя набору требований. Вместо обещания «тип вроде бы должен уметь сравниваться» мы записываем проверяемое условие и связываем его с параметром шаблона. Неподходящий тип исключается из допустимых кандидатов ещё до разбора глубин тела.

В практическом интерфейсе это похоже на проверку пропуска у входа. Функция не ждёт, пока посетитель дойдёт до закрытой лаборатории и попробует неизвестную операцию; она сразу сообщает, какого права не хватает.

Концепты делают сообщения короче, хотя компиляторы всё ещё иногда считают кратким объяснение на половину экрана.

Концепт задаёт именованное ограничение:

```cpp
#include <concepts>

template <typename T>
concept Ordered = requires(const T& first, const T& second) {
    { first > second } -> std::convertible_to<bool>;
};

template <Ordered T>
T maximum(T first, T second) {
    return first > second ? first : second;
}
```

Ограничение не проверяет смысл операции — только доступную форму и свойства результата. Но диагностика и документация интерфейса становятся значительно понятнее.

До C++20 применяли перегрузки, `std::enable_if`, SFINAE и проверки `static_assert`. Они остаются важны для старого кода, но концепт лучше выражает намерение.

### Вычисления времени компиляции

`constexpr` позволяет вычислить выражение при компиляции, когда аргументы и контекст это допускают. Та же функция может выполняться во время работы программы, если получает обычные данные. Ключевое слово задаёт возможность и ограничения, а не безусловное обещание заранее посчитать каждый вызов.

Практический пример — размер таблицы или преобразование фиксированной единицы измерения. Результат можно использовать там, где требуется константное выражение, а ошибка обнаруживается до запуска программы.

Вычисление времени компиляции работает ещё до первого кофе пользователя; компилятору кофе, видимо, приносит система сборки.

Шаблоны исторически использовали для рекурсивных вычислений:

```cpp
template <unsigned N>
struct Factorial {
    static constexpr unsigned value{N * Factorial<N - 1>::value};
};

template <>
struct Factorial<0> {
    static constexpr unsigned value{1};
};
```

Сегодня многие задачи проще записать `constexpr`-функцией:

```cpp
constexpr unsigned factorial(unsigned value) {
    unsigned result{1};
    for (unsigned current{2}; current <= value; ++current) {
        result *= current;
    }
    return result;
}
```

Шаблонное метапрограммирование остаётся полезно, когда результатом вычисления является тип или структура программы.

### Статический полиморфизм

В статическом полиморфизме конкретное поведение известно при формировании специализации. Шаблон вызывает операцию для переданного типа, а компилятор проверяет её наличие и может встроить вызов. Виртуальная диспетчеризация во время выполнения не требуется.

Практически это подходит для алгоритма, который одинаково обрабатывает разные стратегии, выбранные при компиляции. Цена такой гибкости — создание отдельных специализаций и необходимость видеть определения.

Шаблон выбирает поведение при компиляции:

```cpp
template <typename Shape>
double area(const Shape& shape) {
    return shape.area();
}
```

В отличие от виртуального интерфейса, тип конкретного `Shape` известен при инстанцировании. Это называют статическим полиморфизмом. Он не обязательно «быстрее» во всех программах, но не требует виртуального диспетчеризирования и открывает оптимизатору конкретный код.

### Поведение как параметр

Когда функция получает вызываемый объект, она отделяет постоянную последовательность шагов от изменяемого действия. Например, обход набора измерений остаётся одним и тем же, а способ проверки допустимости передаётся параметром.

При вызове шаблон выводит тип функционального объекта. Внутри алгоритма выражение вызова обращается к его `operator()` или другой допустимой форме. Если объект хранит состояние, оно становится частью переданного значения и живёт по обычным правилам C++.

```cpp
template <typename Range, typename Printer>
void printRange(const Range& range, Printer printer) {
    for (const auto& value : range) {
        printer(value);
    }
}
```

Вместо наследования функция получает объект поведения. Им может быть функтор или лямбда. Этот приём лежит в основе алгоритмов стандартной библиотеки.

### Типы предметной области

Шаблон помогает различать значения, которые физически представлены одинаково, но имеют разный смысл:

```cpp
struct MetersTag {};
struct SecondsTag {};

template <typename Tag>
class Quantity {
public:
    explicit Quantity(double value) : value_{value} {}
    double value() const { return value_; }

private:
    double value_;
};

using Meters = Quantity<MetersTag>;
using Seconds = Quantity<SecondsTag>;
```

Теперь метры нельзя случайно передать вместо секунд, хотя оба значения хранят `double`.

### Ошибки исходного учебного `Array`

Пример из `examples/class_template` показывает синтаксис, но не является безопасным контейнером: отсутствует деструктор и копирующие операции, массив освобождается через `delete` вместо `delete[]`, итераторы создаются через `new` и возвращаются по ссылке, а некоторые функции не имеют возвращаемого типа. Использовать этот код как основу реального контейнера нельзя.

Для изучения шаблонов лучше хранить данные в `std::vector<T>` или сосредоточиться на одной операции, не смешивая тему шаблонов с ручным управлением памятью и реализацией итератора.

### Итоги

#### Как читать шаблонный пример целиком

Начнём с места вызова. Конкретные аргументы дают компилятору типы и значения параметров шаблона. Затем проверяются ограничения, выбирается подходящая перегрузка и формируется специализация, если она ещё не была создана в требуемом виде.

Внутри специализации все зависимые выражения получают конкретный смысл. Оператор сравнения относится уже к выбранному типу, размер массива — к переданному нетиповому параметру, а вызываемый объект — к фактическому типу поведения.

Если выражение недопустимо, диагностика относится к этапу компиляции. Концепт может остановить выбор раньше и назвать нарушенное требование; без концепта причина проявится внутри подстановки тела.

Во время выполнения специализация ведёт себя как обычная функция или класс. Параметры шаблона уже не выбираются заново при каждой итерации: решение было принято компилятором.

Практический контроль включает следующие вопросы:

- какие параметры выводятся, а какие заданы явно;
- какие операции требуются от типа;
- видит ли компилятор определение в точке инстанцирования;
- относится ли вычисление к компиляции или к выполнению;
- не возвращает ли функция ссылку на объект с закончившимся временем жизни;
- оправдано ли создание отдельной специализации для каждого варианта.

Такой порядок связывает синтаксис шаблона с реальной механикой генерации кода и помогает читать сообщения об ошибках от внешнего вызова к нарушенному требованию.

Отдельно следует проверить размер результата сборки и время компиляции, если один шаблон создаёт много специализаций. Это не делает шаблоны неправильным выбором, но позволяет увидеть реальную цену универсальности.

Если специализации используют одну и ту же тяжёлую операцию, общую нешаблонную часть иногда можно отделить. Такое решение остаётся в рамках той же темы: шаблон отвечает за различия типов, обычная функция — за поведение, не зависящее от них.

В учебном примере достаточно сначала доказать корректность одной специализации, затем второй. Сравнение помогает отделить общий алгоритм от требований, случайно связанных с первым типом.

После этого новые типы проверяются уже относительно явно сформулированного контракта.

Шаблон отделяет неизменный алгоритм от типа или значения, с которым он работает. Концепты делают требования явными, `constexpr` переносит подходящие вычисления на этап компиляции, а передача поведения параметром создаёт статический полиморфизм без иерархии классов.
