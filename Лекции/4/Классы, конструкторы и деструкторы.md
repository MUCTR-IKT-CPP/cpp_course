### От задачи к объекту

Объектно-ориентированный подход предлагает описывать программу через сущности предметной области, их состояние и допустимые действия. Он не отменяет функции или структурный подход, а добавляет ещё один способ организовать сложность.

**Абстрагирование** означает, что мы выделяем важные для задачи свойства и сознательно отбрасываем остальные. Автомобиль в программе проката и автомобиль в симуляторе двигателя будут разными абстракциями, хотя объект реального мира один.

ООП полезно, когда состояние и операции естественно образуют единое понятие. Но классы не следует создавать ради самого факта «объектности»: лишние иерархии и скрытое изменяемое состояние способны усложнить программу.

### Класс и объект

#### Практическая модель объекта

Представим заказ в интернет-магазине. У него есть номер, набор позиций и текущее состояние, а также операции добавления товара и подтверждения оплаты. Если хранить эти данные в независимых переменных, ничто не помешает забыть обновить одну из них. Класс собирает связанное состояние и допустимые действия в одной модели.

Объект появляется не в момент написания класса, а во время выполнения программы, когда вызывается конструктор. Для двух объектов одного класса код методов общий, но состояние раздельно: изменение одного заказа не должно менять другой, если мы явно не связали их общим ресурсом.

При чтении метода полезно задавать три вопроса: над каким объектом он вызван, какие поля прочитает и какие поля изменит. Такой разбор быстро показывает, является ли операция наблюдением или меняет инвариант объекта.


**Класс** определяет пользовательский тип, его данные и операции. **Объект** — конкретный экземпляр этого типа.

```cpp
class Point {
public:
    double x{0.0};
    double y{0.0};

    void shift(double dx, double dy) {
        x += dx;
        y += dy;
    }
};

Point origin;
origin.shift(1.0, 2.0);
```

Пока поля открыты, любой код может менять их напрямую. Инкапсуляцию и спецификаторы доступа подробно разберём в следующей лекции.

### Конструктор

#### Что происходит при создании

Конструктор не создаёт память для объекта сам по себе. Сначала вызывающий контекст предоставляет подходящее хранилище: автоматическое, динамическое или часть другого объекта. Затем начинается инициализация базовых частей и полей, и только после неё выполняется тело конструктора.

Именно поэтому список инициализации имеет принципиальное значение. Поле не «сначала отсутствует, а затем получает значение в теле»: к моменту входа в тело оно уже должно быть сконструировано. Присваивание в теле для сложного поля может означать лишнюю работу — сначала создание состояния по умолчанию, затем его замену.

В прикладном объекте `Connection` список инициализации может сохранить адрес сервера и подготовить внутренний ресурс. Если один из шагов завершается исключением, полностью созданного объекта ещё нет, а уже построенные части будут корректно уничтожены.


**Конструктор** создаёт корректное начальное состояние объекта. У него имя класса и нет возвращаемого типа:

```cpp
class Point {
public:
    Point(double x, double y)
        : x_{x}, y_{y} {}

private:
    double x_;
    double y_;
};
```

Часть после двоеточия — **список инициализации членов**. Это не «короткий конструктор присвоения»: поля инициализируются до входа в тело конструктора, а не сначала создаются и затем получают значения.

Члены всегда инициализируются в порядке их объявления в классе, а не в порядке списка. Лучше писать список в том же порядке, чтобы код не вводил читателя в заблуждение.

### Конструктор по умолчанию

Наличие конструктора без аргументов отвечает на предметный вопрос: существует ли осмысленное начальное состояние без дополнительных данных? Для счётчика ответ обычно положительный — он может начинаться с нуля. Для банковского перевода без отправителя, получателя и суммы такое состояние уже сомнительно.

Если мы явно объявили другой конструктор, автоматическое предоставление конструктора по умолчанию меняется. Запись `= default` не «обнуляет всё», а просит компилятор сформировать обычную реализацию там, где это допустимо. Начальные значения полей при этом определяются их собственными инициализаторами и правилами языка.

Конструктор по умолчанию можно вызвать без аргументов:

```cpp
class Point {
public:
    Point() = default;
    Point(double x, double y) : x_{x}, y_{y} {}

private:
    double x_{0.0};
    double y_{0.0};
};
```

Компилятор не всегда автоматически предоставляет такой конструктор. Например, объявление другого пользовательского конструктора подавляет неявное объявление конструктора по умолчанию. Запись `= default` позволяет запросить стандартное поведение явно, если оно возможно для всех членов и базовых классов.

### Копирующий конструктор

#### Независимость копии

Копирование удобно представить как создание второго документа по образцу первого. Значения переносятся, но дальнейшее редактирование копии не должно неожиданно менять оригинал. Для полей-значений это поведение получается естественно; для сырого указателя простое копирование адреса связывает два объекта с одной областью памяти.

Если класс владеет динамическим ресурсом, копирующий конструктор должен определить смысл копии. Глубокое копирование создаёт новый ресурс и переносит содержимое. Разделяемое владение оставляет ресурс общим, но тогда это решение должно быть выражено подходящим типом и правилами времени жизни.

В примере с буфером нужно проследить последовательность: выделяется новая память нужного размера, элементы копируются, указатель нового объекта связывается с новым блоком. После этого уничтожение одного буфера не затрагивает второй.

Копирование сырого указателя выполняется мгновенно; понимание того, кто теперь владелец, иногда занимает остаток рабочего дня.

Копирующий конструктор создаёт новый объект из существующего:

```cpp
class Point {
public:
    Point(const Point& other)
        : x_{other.x_}, y_{other.y_} {}
};
```

Для полей-значений неявное почленное копирование обычно корректно. Проблема возникает, когда класс вручную владеет ресурсом через сырой указатель:

```cpp
class Sample {
public:
    explicit Sample(double value)
        : error_{new double{value}} {}

    Sample(const Sample& other)
        : error_{new double{*other.error_}} {}

    ~Sample() {
        delete error_;
    }

private:
    double* error_;
};
```

Если скопировать только адрес, два объекта будут считать себя владельцами одной области и попытаются удалить её дважды. Поэтому требуется глубокое копирование. Ещё лучше заменить указатель обычным `double` или подходящим RAII-типом и избавиться от ручного управления.

### Перемещающий конструктор

#### Передача владения

Перемещение применяется, когда исходный объект разрешено использовать как источник ресурсов. Новый объект принимает, например, указатель и размер, а исходный переводится в корректное состояние без владения. Дорогого копирования элементов при этом не происходит.

Состояние перемещённого объекта остаётся допустимым, но его конкретное содержимое обычно не следует предполагать без явного контракта типа. Его можно уничтожить или присвоить ему новое значение. Проверка старых данных после перемещения превращает оптимизацию в лотерею предположений.

Важно различать `std::move` и сам перемещающий конструктор. Первый лишь разрешает рассматривать выражение как источник; второй действительно переподключает владение.

Перемещение позволяет новому объекту забрать ресурс у объекта, который больше не нужен:

```cpp
Sample(Sample&& other) noexcept
    : error_{other.error_} {
    other.error_ = nullptr;
}
```

Перемещающий конструктор принимает `T&&`. Перемещённый объект должен оставаться корректным для уничтожения и присваивания, но его прежнее значение обычно не гарантируется.

Компилятор не обещает автоматически создать перемещающие операции для любого класса. Их неявное объявление зависит от других специальных функций-членов и возможности переместить поля. Пользовательский деструктор или копирующие операции способны подавить генерацию перемещения.

### Копирующее и перемещающее присваивание

#### Почему присваивание сложнее создания

Конструктор работает с новым хранилищем, а оператор присваивания — с уже живым объектом. Значит, перед принятием нового состояния нужно корректно освободить или заменить старое. Кроме того, выражение `a = a` не должно уничтожить данные до того, как они будут прочитаны.

При копирующем присваивании полезно сначала подготовить новое состояние, а затем заменить старое. Такой порядок облегчает сохранение объекта при ошибке выделения памяти. При перемещающем присваивании объект освобождает свой текущий ресурс, принимает ресурс источника и оставляет источник допустимым для уничтожения.

Практический сценарий — повторная загрузка изображения в уже существующий объект. Создание отвечает за первую загрузку, присваивание — за безопасную замену ранее загруженного содержимого.

Самоприсваивание редко планируют специально, но код иногда находит его самостоятельно — у него вообще талант к неожиданным знакомствам.

Конструктор создаёт новый объект, присваивание меняет уже существующий:

```cpp
class Sample {
public:
    Sample& operator=(const Sample& other);
    Sample& operator=(Sample&& other) noexcept;
};
```

Оператор обычно возвращает `*this` по ссылке, поддерживает цепочку присваиваний и корректно обрабатывает самоприсваивание. Перед получением нового ресурса он обязан безопасно освободить старый.

Типичная сигнатура со слайда без `&` у возвращаемого типа создаёт лишнюю копию и не является обычной формой оператора присваивания.

### `= default` и `= delete`

```cpp
class Identifier {
public:
    Identifier() = default;
    Identifier(const Identifier&) = delete;
    Identifier& operator=(const Identifier&) = delete;
};
```

`= default` просит сформировать стандартную реализацию специальной функции, если она допустима. `= delete` объявляет функцию запрещённой и даёт понятную ошибку при попытке её вызвать.

Эти спецификаторы применимы не только к конструкторам. Удалить можно перегрузку обычной функции, а явно определить по умолчанию — подходящую специальную функцию-член.

### Деструктор

#### Завершение времени жизни

Деструктор вызывается, когда время жизни объекта заканчивается: при выходе автоматического объекта из блока, при уничтожении содержащего объекта или через корректного владельца динамического объекта. Его задача — завершить владение ресурсами, которые объект приобрёл.

Для файла это закрытие дескриптора, для блокировки — освобождение мьютекса, для динамического буфера — освобождение памяти. Пользователь класса не обязан помнить отдельную функцию очистки: достаточно позволить объекту завершить жизнь обычным образом.

Порядок уничтожения обратен порядку построения. Сначала выполняется тело деструктора наиболее производного объекта, затем уничтожаются его поля и базовые части в установленном порядке. Это важно, потому что код деструктора не должен обращаться к уже уничтоженной зависимости.

Деструктор — сотрудник, который закрывает офис последним и почему-то всегда знает, кто оставил включённый свет.

**Деструктор** выполняется при завершении времени жизни объекта:

```cpp
class Sample {
public:
    ~Sample() {
        delete error_;
    }
};
```

Его имя начинается с `~`, он не принимает параметров и не имеет возвращаемого типа. Деструктор нужен не для «очистки памяти класса» вообще, а для освобождения ресурсов, которыми владеет объект. Память самого автоматического объекта освобождает среда выполнения после вызова деструктора.

Если все поля сами корректно управляют ресурсами, пользовательский деструктор обычно не нужен.

### Указатель `this`

`this` связывает общий код метода с конкретным объектом вызова. В выражении `order.confirm()` внутри `confirm` указатель `this` указывает на `order`, поэтому обращение к полю фактически относится к `this->field`.

Практически это позволяет отличить поле от одноимённого параметра и вернуть текущий объект из метода. При этом `this` не является дополнительным владельцем и не продлевает время жизни. Сохранить его где-то можно только при уверенности, что объект переживёт последующее использование указателя.

В нестатической функции-члене `this` указывает на текущий объект:

```cpp
class Point {
public:
    Point(double x, double y)
        : x_{x}, y_{y} {}

    Point& shiftX(double shift) {
        this->x_ += shift;
        return *this;
    }

private:
    double x_;
    double y_;
};
```

Обычно `this->` можно опустить. Оно полезно для устранения неоднозначности и в некоторых шаблонных контекстах. Формулировка «компилятор фактически вызывает обычную функцию с `&obj`» является удобной моделью, но не буквальным правилом исходного языка.

### Цепочки вызовов

Цепочка работает, когда метод возвращает ссылку на тот же объект. Сначала выполняется левый вызов и изменяет состояние, затем следующий получает возвращённую ссылку и продолжает работу с тем же экземпляром. Промежуточная копия не требуется.

Так удобно настраивать объект: `builder.setWidth(10).setHeight(20)`. Однако каждый шаг должен оставлять объект в допустимом состоянии либо вся цепочка становится красивой записью последовательности частично выполненных обещаний.

Цепочки вызовов делают код похожим на предложение; главное, чтобы это предложение не оказалось юридическим договором на четыре экрана.

Возврат `*this` по ссылке позволяет связать вызовы:

```cpp
point.shiftX(5.0).shiftY(-2.0).print();
```

Для такого интерфейса ссылка естественнее указателя: объект обязателен, а пользователю не приходится писать `->`. Цепочка хороша, когда операции логически образуют последовательную настройку. Если методы скрыто меняют несвязанные части состояния, цепочка ухудшает читаемость.

### RAII

#### Практическая механика RAII

Представим функцию, которая открывает файл, читает заголовок и может завершиться в нескольких местах. При ручном закрытии каждый новый `return` требует помнить об очистке. RAII переносит эту обязанность в объект-владелец: файл открывается при построении, а закрывается в деструкторе независимо от выбранной ветви выхода.

Механика опирается на область видимости. Пока локальный владелец существует, ресурс доступен. Когда выполнение покидает блок обычным путём или из-за исключения, деструктор вызывается автоматически. Поэтому управление ресурсом становится частью правил языка, а не дисциплины автора каждой функции.

RAII применимо не только к памяти. Тем же способом управляют файлами, блокировками, соединениями и временными настройками. Общая идея одна: состояние «ресурс захвачен» принадлежит объекту с чётким временем жизни.

RAII — это когда уборка происходит сама; редкая разновидность магии, которая на самом деле подробно описана стандартом.

**RAII** связывает владение ресурсом со временем жизни объекта. Ресурс получают в конструкторе или фабрике, а освобождают в деструкторе. Это относится не только к памяти, но и к файлам, блокировкам, сокетам и транзакциям.

```cpp
void processFile() {
    std::ifstream input{"data.txt"};
    if (!input) {
        return;
    }
    // файл закроется автоматически при выходе из функции
}
```

RAII делает досрочный `return` и исключения безопаснее: деструкторы автоматических объектов всё равно будут вызваны.

### Правила нуля, трёх и пяти

Правило нуля предлагает передать владение готовым типам: строкам, контейнерам и умным указателям. Тогда сгенерированные компилятором операции обычно уже делают нужное, а класс описывает предметную логику вместо ручной работы с ресурсом.

Если класс напрямую владеет ресурсом и требует пользовательского деструктора, нужно совместно продумать копирование и присваивание — отсюда правило трёх. После появления перемещения набор расширяется до пяти. Это не формальный приказ написать пять функций, а сигнал проверить согласованность семантики.

На практике решение начинается с вопроса о владении. Если класс не обязан владеть сырым ресурсом, правило нуля уменьшает объём кода и число состояний, которые приходится доказывать корректными.

Если класс вручную управляет ресурсом и объявляет деструктор, копирующий конструктор или копирующее присваивание, обычно нужно проверить все три операции — это **правило трёх**.

После появления перемещения набор расширился до пяти: деструктор, копирующий конструктор, копирующее присваивание, перемещающий конструктор и перемещающее присваивание.

Предпочтительнее **правило нуля**: хранить ресурсы в `std::string`, контейнерах, умных указателях и других RAII-типах, чтобы не писать ни одну из пяти функций вручную.

```cpp
class Person {
public:
    Person(std::string name, std::vector<int> scores)
        : name_{std::move(name)}, scores_{std::move(scores)} {}

private:
    std::string name_;
    std::vector<int> scores_;
};
```

Такой класс естественно копируется, перемещается и уничтожается благодаря поведению его полей.

### Итоги

#### Как проследить полный жизненный цикл

При чтении класса полезно собрать операции в одну временную линию. Сначала определяется хранилище объекта, затем инициализируются его части, после чего выполняется тело конструктора. Между созданием и уничтожением методы поддерживают инвариант, а в конце деструктор освобождает принадлежащие объекту ресурсы.

Для копии временная линия начинается новым конструктором и новым состоянием. Для присваивания исходный объект уже существует, поэтому старое состояние требуется безопасно заменить. Для перемещения дополнительно нужно проследить, какой экземпляр стал владельцем и в каком допустимом состоянии остался источник.

Практическая проверка класса включает четыре вопроса:

- может ли объект появиться сразу в корректном состоянии;
- кто владеет каждым ресурсом;
- независимы ли копии и безопасно ли перемещение;
- освобождаются ли ресурсы при любом выходе из области видимости.

Если ответы видны из типов полей и небольшого интерфейса, класс следует правилу нуля и требует меньше ручных доказательств корректности.

Конструктор не просто присваивает полям значения, а формирует инвариант объекта. Копирование создаёт независимое состояние, перемещение может передать владение, а деструктор завершает работу с ресурсом. Чем лучше поля класса выражают владение самостоятельно, тем меньше специальных функций приходится писать вручную.
