### Три механизма на основе абстракции

Абстракция помогает говорить о существенном, не перечисляя детали реализации при каждом обращении. В системе доставки нас интересует операция расчёта стоимости, а не устройство каждого конкретного тарифа. Класс задаёт модель, наследование может выразить специализацию, а полиморфизм позволяет выбрать реализацию через общий контракт.

Эти механизмы связаны, но не тождественны. Наличие базового класса ещё не создаёт динамического поведения, а сокрытие полей само по себе не делает модель удачной. В каждом примере будем отделять отношение между типами, доступ к состоянию и выбор выполняемой функции.


Класс становится полезной абстракцией не только потому, что объединяет поля и методы. Объектная модель C++ предоставляет три связанных механизма:

- **инкапсуляция** управляет доступом к состоянию;
- **наследование** описывает отношение базового и производного типов;
- **полиморфизм** позволяет использовать общий интерфейс для разного поведения.

Эти механизмы не обязаны встречаться вместе. Хорошая композиция объектов часто проще и надёжнее глубокой иерархии наследования.

### Наследование

#### Предметный смысл отношения

Наследование оправдано, когда объект производного типа можно использовать там, где ожидается базовый, не нарушая смысл обещаний. Например, разные варианты уведомлений могут поддерживать общую операцию отправки. Пользователь контракта просит отправить сообщение и не обязан знать внутренний протокол.

При создании производного объекта сначала строится его базовая часть, затем поля производного класса и только после этого выполняется тело его конструктора. Уничтожение идёт в обратном порядке. Поэтому производная часть может рассчитывать на уже созданную базовую, но базовый конструктор ещё не может использовать состояние, которое появится позднее.

Доступ к унаследованному члену и наличие этого члена — разные вопросы. Закрытая часть базового объекта физически остаётся внутри производного, хотя обращаться к ней напрямую нельзя. Взаимодействие проходит через доступный интерфейс базового класса.

Наследование похоже на семейный архив: получить историю можно автоматически, а вот разобраться, что из неё действительно нужно, приходится отдельно.

**Наследование** создаёт производный класс на основе базового:

```cpp
class Weapon {
public:
    explicit Weapon(std::string name)
        : name_{std::move(name)} {}

    const std::string& name() const {
        return name_;
    }

private:
    std::string name_;
};

class Sword : public Weapon {
public:
    Sword(std::string name, double length)
        : Weapon{std::move(name)}, length_{length} {}

private:
    double length_;
};
```

Семейная аналогия со слайдов помогает увидеть направление: производный тип получает доступную часть поведения базы и добавляет своё. Однако программное наследование точнее читать как отношение **is-a**: объект `Sword` можно корректно использовать там, где ожидается `Weapon`.

Конструктор производного класса сначала инициализирует базовую часть, затем собственные поля. Деструкторы выполняются в обратном порядке.

### Когда наследование не подходит

Представим отчёт, который использует принтер. Отчёт не является разновидностью принтера; он лишь обращается к нему для вывода. Наследование исказило бы предметный смысл и связало две сущности сильнее, чем требуется. Хранение отдельного объекта или ссылки выражает отношение «использует» точнее.

Композиция позволяет заменить часть поведения без изменения иерархии. Это особенно полезно, когда компонент имеет самостоятельное время жизни или несколько реализаций. Однако выбор делается по смыслу модели, а не по лозунгу: иногда наследование действительно является правильным отношением.

Если `Car` наследуется от `Engine`, автомобиль формально становится двигателем; механик удивится, компилятор — нет.

Если объект лишь содержит другой объект или временно использует его, это отношение **has-a**, и композиция обычно естественнее:

```cpp
class Car {
private:
    Engine engine_;
};
```

Наследование ради повторного использования нескольких строк кода создаёт сильную связь и может нарушить взаимозаменяемость типов.

### Инкапсуляция

#### Инвариант в практической модели

У банковского счёта баланс не должен произвольно становиться отрицательным, если правила продукта этого не разрешают. Закрытое поле и операции пополнения и списания собирают проверку в одном месте. Пользователь объекта выражает намерение «списать сумму», а класс сохраняет собственные ограничения.

Инкапсуляция не означает механическое создание пары `get`/`set` для каждого поля. Если внешний код может записать любое значение через сеттер, состояние фактически остаётся открытым, только синтаксис становится длиннее. Полезный интерфейс отражает допустимые действия предметной области.

В примере метода важно проследить последовательность: проверяются входные данные, затем изменяется состояние, после чего инвариант снова должен выполняться. Если операция не может завершиться, объект следует оставить в согласованном состоянии.

**Инкапсуляция** объединяет состояние с операциями и ограничивает способы нарушения инварианта.

```cpp
class Account {
public:
    explicit Account(long long balance)
        : balance_{balance} {
        if (balance < 0) {
            throw std::invalid_argument{"negative balance"};
        }
    }

    long long balance() const {
        return balance_;
    }

    void deposit(long long amount) {
        if (amount <= 0) {
            throw std::invalid_argument{"non-positive deposit"};
        }
        balance_ += amount;
    }

private:
    long long balance_;
};
```

Закрытое поле полезно не само по себе. Польза появляется, когда открытые операции поддерживают понятные правила состояния.

Спецификаторы доступа:

- `public` — имя доступно пользователям типа;
- `protected` — доступно классу и его производным классам;
- `private` — доступно самому классу и его друзьям.

Члены `private` существуют в базовой части производного объекта, но производный класс не может обращаться к ним напрямую.

### Режимы наследования

Режим наследования определяет, как доступность членов базового интерфейса преобразуется для пользователей производного типа. При `public` наследовании публичная часть базового класса остаётся публичной: этим обычно выражают отношение подстановки.

`protected` и `private` наследование меняют доступность и чаще описывают использование реализации, а не открытую разновидность базового типа. Здесь важно не путать два уровня: спецификатор у отдельного члена и режим наследования всей базовой части отвечают на разные вопросы.


Режим после двоеточия преобразует доступ унаследованных `public` и `protected` членов:

| Наследование | `public` базы становится | `protected` базы становится |
| --- | --- | --- |
| `public` | `public` | `protected` |
| `protected` | `protected` | `protected` |
| `private` | `private` | `private` |

`private` члены базы остаются недоступны напрямую во всех вариантах.

Открытое наследование выражает отношение взаимозаменяемых типов. Закрытое и защищённое наследование чаще являются деталями реализации и требуют отдельного обоснования.

### Полиморфизм

#### Как выбирается поведение

Пусть функция получает ссылку на базовый тип уведомления, а фактический объект представляет электронную почту. Статический тип ссылки определяет, какие операции разрешено вызвать, а динамический тип объекта участвует в выборе переопределённой виртуальной функции.

Во время виртуального вызова программа находит реализацию, соответствующую фактическому объекту. Поэтому одна функция обхода может работать с набором разных уведомлений, вызывая одно и то же имя операции, но получая разное поведение.

Это не отменяет контракт базового класса. Производная реализация должна сохранять ожидаемый смысл операции. Если один тип под именем `send` отправляет сообщение, а другой удаляет адресата, техническая подстановка возможна, но модель сломана.

Полиморфизм позволяет одному вызову иметь много форм; совещание с таким названием обычно имеет много участников и ни одной формы протокола.

В широком смысле **полиморфизм** — возможность работать с разными типами через общий способ обращения. В C++ есть несколько форм:

- перегрузка функций и операторов;
- шаблоны;
- динамический полиморфизм через виртуальные функции.

На этом этапе достаточно увидеть общий замысел:

```cpp
class Vehicle {
public:
    virtual void start() = 0;
    virtual ~Vehicle() = default;
};

class Car : public Vehicle {
public:
    void start() override {
        std::cout << "Запускаем двигатель\n";
    }
};
```

Код, принимающий `Vehicle&`, сможет вызвать `start`, не зная конкретный вид транспорта. Механизм виртуального вызова подробно рассматривается в следующей лекции.

### Дружественные функции

Дружественная функция не становится методом и не получает собственного `this`. Класс лишь явно разрешает ей обращаться к закрытой части конкретных объектов. Это полезно, когда операция симметрична относительно нескольких аргументов или левый операнд не является нашим классом.

Практический пример — потоковый вывод: левым операндом служит `std::ostream`, который мы не изменяем, а правым — пользовательский объект. Дружба даёт функции доступ к представлению объекта, но пользоваться этим следует точечно, чтобы не размывать границу инкапсуляции.

Дружественная функция не является методом, но получает доступ к закрытым и защищённым членам:

```cpp
class PrintedInt {
public:
    explicit PrintedInt(int value) : value_{value} {}

    friend std::ostream& operator<<(std::ostream&, const PrintedInt&);

private:
    int value_;
};

std::ostream& operator<<(std::ostream& output, const PrintedInt& value) {
    return output << value.value_;
}
```

Дружба выдаёт привилегированный доступ, поэтому её стоит использовать локально. Она не наследуется, не является взаимной автоматически и не создаёт указатель `this`.

### Перегрузка операторов

#### От синтаксиса к вызову функции

Выражение с перегруженным оператором остаётся вызовом функции с особыми правилами записи. Для `a + b` компилятор собирает подходящие кандидаты, учитывает типы операндов и выбирает лучшую перегрузку. После выбора выполняется обычный код этой функции.

Практический смысл оператора должен совпадать с ожиданиями читателя. Сложение координат или конкатенация строк выглядят естественно; оператор `+`, который сохраняет объект в файл, технически возможен, но скрывает действие и побочные эффекты.

В разборе примера важно отметить, создаётся ли новый результат или изменяется левый операнд, какие преобразования допускаются и что возвращается для последующих выражений.

Перегрузить можно почти любой доступный оператор, но чувство меры, к сожалению, отдельной перегрузки не имеет.

Перегрузка задаёт поведение оператора для пользовательского типа:

```cpp
class Distance {
public:
    explicit Distance(double meters) : meters_{meters} {}

    Distance& operator+=(const Distance& other) {
        meters_ += other.meters_;
        return *this;
    }

    friend Distance operator+(Distance left, const Distance& right) {
        left += right;
        return left;
    }

private:
    double meters_;
};
```

Оператор остаётся функцией. Нельзя изменить его приоритет, количество операндов или придумать новый символ. Поведение должно быть ожидаемым: `+` обычно не меняет аргументы, а `+=` меняет левый.

Не все операторы можно перегрузить; среди запрещённых, например, `.`, `.*`, `::`, `?:` и `sizeof`. Перегруженные `&&` и `||` не следует использовать как замену встроенным логическим операторам: пользовательская перегрузка не даёт их обычной семантики сокращённого вычисления.

### Потоковый оператор

Оператор `<<` принимает поток слева и объект справа, записывает представление и возвращает тот же поток по ссылке. Возврат позволяет следующему оператору в цепочке получить уже изменённый поток: сначала выводится объект, затем разделитель, затем следующее значение.

Функция не должна создавать новый поток или возвращать копию. Состояние форматирования и ошибки принадлежат исходному объекту потока, поэтому все звенья цепочки должны работать именно с ним.

`operator<<` обычно является свободной функцией, потому что левый операнд — поток:

```cpp
std::ostream& operator<<(std::ostream& output, const PrintedInt& value) {
    return output << "PrintedInt{" << value.value_ << '}';
}
```

Возврат потока по ссылке поддерживает цепочку `std::cout << first << second`.

### Некопируемый тип

Некоторые объекты представляют уникальный ресурс: системный дескриптор, блокировку или соединение, у которого в каждый момент должен быть один ответственный владелец. Удаление копирующих операций выражает это правило на уровне типа. Попытка случайно скопировать объект останавливается при компиляции, а не превращается в двойное освобождение позднее.

Запрет копирования не запрещает передачу объекта вообще. Тип может поддерживать перемещение, если владение разрешено передать. Тогда исходный объект лишается ресурса, а новый становится единственным владельцем.


Современный способ запретить копирование — явно удалить операции:

```cpp
class UniqueHandle {
public:
    UniqueHandle(const UniqueHandle&) = delete;
    UniqueHandle& operator=(const UniqueHandle&) = delete;

    UniqueHandle(UniqueHandle&&) noexcept = default;
    UniqueHandle& operator=(UniqueHandle&&) noexcept = default;
};
```

Старый приём с закрытым необъявленным конструктором копирования даёт менее понятную диагностику и сегодня не нужен.

### Контролируемое создание

Закрытый конструктор не позволяет внешнему коду создавать объект произвольным способом. Открытая фабричная функция может проверить данные, выбрать конкретную реализацию или вернуть признак неудачи. Тем самым класс контролирует момент, когда его инварианты впервые становятся истинными.

При чтении примера нужно разделить выделение памяти и предметное решение. Фабрика определяет, можно ли и какой объект создать; выбранный механизм владения определяет, кто затем отвечает за его время жизни.

Фабрика объектов работает лучше обычной фабрики хотя бы тем, что требования к продукции проверяет компилятор.

Закрытый конструктор позволяет передать создание фабричной функции:

```cpp
class Configuration {
public:
    static Configuration& instance() {
        static Configuration value;
        return value;
    }

    Configuration(const Configuration&) = delete;
    Configuration& operator=(const Configuration&) = delete;

private:
    Configuration() = default;
};
```

Такой код похож на паттерн «Одиночка», но закрытый конструктор сам по себе не гарантирует единственность: нужно также запретить копирование и контролировать все фабрики. Глобально доступное изменяемое состояние усложняет тестирование, поэтому одиночку нельзя считать универсальным решением.

### Итоги

#### Сквозной разбор полиморфной модели

Представим список способов доставки. Создающая часть программы выбирает конкретные объекты, а расчёт получает ссылки на общий базовый контракт. Статический тип ссылки разрешает вызвать расчёт стоимости, динамический тип выбирает реализацию конкретной доставки.

Чтобы схема оставалась корректной, каждый производный тип должен принимать допустимые для базы входные данные и возвращать результат в обещанных границах. Если один вариант требует совершенно другого контракта, его не следует встраивать в иерархию только ради общего контейнера.

Время жизни также остаётся частью модели. Если контейнер владеет объектами через базовые указатели, владелец должен явно выражать освобождение, а базовый класс — поддерживать корректное полиморфное уничтожение. Сама ссылка, переданная функции расчёта, владельцем не становится.

Инкапсуляция удерживает внутреннее состояние каждой доставки согласованным. Внешний код не меняет тариф произвольно, а вызывает операции, которые проверяют условия и оставляют объект в допустимом состоянии.

Для проверки решения можно последовательно спросить:

- выражает ли наследование отношение подстановки;
- можно ли использовать базовый контракт без проверки конкретного типа;
- сохраняют ли производные классы обещания базы;
- не открыт ли инвариант через публичные поля или универсальные сеттеры;
- понятен ли владелец полиморфных объектов;
- соответствует ли перегруженный оператор привычному смыслу операции.

Такой анализ связывает наследование, инкапсуляцию и полиморфизм в одну причинную модель, а не в три независимых определения.

При изменении требований тот же анализ показывает, какая граница контракта действительно должна измениться.

Он также показывает, какое обещание проверять при дальнейшем изменении каждого класса.

Наследование выражает отношение типов, инкапсуляция защищает инварианты, а полиморфизм отделяет общий интерфейс от конкретного поведения. Дружественные функции и операторы способны сделать тип естественным в использовании, если сохраняют ожидаемую семантику. Контроль доступа — инструмент проектирования, а не цель сам по себе.
